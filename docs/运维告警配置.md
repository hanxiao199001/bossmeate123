# 运维告警配置说明（给运营看的）

> 一句话：这套东西让系统**自己喊救命**。以前出问题只写进服务器日志、没人看得到，
> 系统停摆好几天都没人发现；现在系统每天主动给你发一条微信，出事了还会被外部拨测服务电话/邮件叫醒。

一共三件事：

| # | 是什么 | 你会怎么感知到 |
|---|---|---|
| 1 | **每日运营简报** | 每天早上 **09:30**，企业微信收到一条《BossMate 运维简报》 |
| 2 | **余额/欠费告警** | AI 快没钱了、或者今天突然一分钱没花（多半是欠费），简报里红字告诉你 |
| 3 | **健康拨测** | 服务器整个挂了，UptimeRobot 直接发邮件/短信叫你（不依赖我们自己的系统） |

## 〇、无人值守必做（老板几个月不看系统之前，这一节逐条打勾）

系统"能自己活着、出事能喊到人"，靠的是下面四道保险。前三道是系统内置的（装好即有），
**第 ④ 条必须人工配置一次，没配等于裸奔**：

| ✔ | 保险 | 是什么 / 怎么确认 |
|---|---|---|
| ☐ | ① 每日简报 + 连续异常强告警 | 简报每天 09:30 到企微。**连续 3 天零产出/零分发**时标题会变成 `🚨🚨【BossMate 强告警】`——收到这个标题 = 系统真死了没人管，当天必须找人处理（天数在 `.env` 的 `OPS_ZERO_STREAK_DAYS` 调） |
| ☐ | ② LLM 花费硬上限 | 防"程序 bug 疯狂重试一夜烧光余额"。默认 **50 元/天、2000 次/天**（日常用量的 10 倍，正常放量碰不到）。触顶当天**停止内容生成**（AI 客服不受影响），第二天零点自动恢复，简报红字说明原因。调整：`.env` 里 `LLM_DAILY_COST_CAP_YUAN` / `LLM_DAILY_CALL_CAP`；设 0 = 该项不限 |
| ☐ | ③ 简报推送重试 | 企微偶发抽风时自动重试 3 次；仍失败会落库到「今日驾驶舱」卡片并记异常。无需配置 |
| ☐ | ④ **UptimeRobot 外部拨测（唯一必须人工做的）** | **服务器整个挂了，上面 ①②③ 全部失效**——简报发不出、告警落不了库，系统内的一切告警都是"用系统自己喊系统挂了"，死循环。外部拨测是唯一保险。**没配这条，宕机可以无人知晓地持续几周。**照下方"三、外部健康拨测"一步步配（10 分钟）：监控 `https://域名/api/v1/health/ping`，5 分钟一次，告警联系人**务必加手机短信**，不要只留邮箱 |

配完 ④ 之后做一次演习：让技术把服务停 10 分钟（`pm2 stop`），确认 UptimeRobot 的 Down 告警
真的到了手机上，再 `pm2 start` 恢复。**没演习过的告警等于没有告警。**

另外两件交接常识：
- 抖音/视频号是**人工上传**运营（系统出片 → 运营下载 → 手机上传），这些号在「账号矩阵」里应设为
  「人工上传」模式（支持多选批量设置）——否则简报每天误报十几条"助手离线"，把真告警淹掉。
- 简报里「📋 今日待办」段就是运营每天的活：几条视频待上传、几个号要重新扫码、几条内容待复核。
  待办可以攒一两天，🔴 红色段不行。

## 一、每日运营简报

### 1.1 长什么样

```
【BossMate 运维简报】2026-07-25

🔴 需要立刻处理
· 今日内容生成 0 篇 —— 生成链路可能整条停了。先看 AI 额度是否用尽，再看服务器日志 daily-recommendation。
· 2 条发布任务超过 10 分钟没被领取 —— 客户电脑上的发布助手没开机或掉线，请提醒客户启动。

🟡 今天内看一眼
· 3 个公众号今日进草稿箱未达保底(2 篇/天): 学术加油站(1/2)、科研直通车(0/2)、期刊速递(1/2) —— 内容不够分，需提高生成量。
· AI 客服今日转人工 7 次 —— 到「AI 客服」页看"没答上"清单，顺手补进 FAQ。

— 今日概况 —
系统健康: 正常
XX 科技: 生成 12 条 · 进草稿箱 6 条 · 发布 5 条 · 账号 5(异常 0) · 今日花费 12.30 元 / 预算已用 12%
阿里云账户余额: 1234.50 元

详情打开「今日驾驶舱」。本简报每天自动发送一次(正常也发，没收到=简报本身出问题了)。
```

### 1.2 三条阅读规则

1. **🔴 红色 = 现在就得动手。** 不处理今天就白跑了（内容发不出去 / 系统在停摆 / 钱花完了）。
2. **🟡 黄色 = 今天内看一眼。** 不致命，但放着会慢慢变差。
3. **没有红黄两段 = 一切正常。** 简报**正常也会发** —— 这是故意的：如果哪天你**没收到**简报，
   说明**简报本身出问题了**（服务挂了 / 企微配置坏了），这本身就是一个告警。

### 1.3 收不到简报怎么办

简报走**企业微信自建应用**推送，用的是 AI 客服那套凭证。收不到按顺序查：

1. 打开系统「**今日驾驶舱**」，最上面有一张**运维简报卡片** —— 只要系统还活着，
   哪怕微信推送失败，这张卡片里也一定有当天的简报（推送失败会在卡片底部写明原因）。
2. 卡片说"没能推送到企业微信" → 去「**AI 客服 → 企微设置**」，把
   **自建应用 Secret** 和 **接收通知的成员** 补齐，再点卡片右上角「**立即体检**」重试一次。
3. 卡片本身也打不开（网页进不去） → 说明服务器挂了，看下面第三节的拨测告警。

### 1.4 想现在就看一份 / 改推送对象

- **马上生成一份**：今日驾驶舱 → 运维简报卡片右上角 → **「立即体检」**。会当场重新体检并再推一次企业微信。
- **改接收人**：「AI 客服 → 企微设置」里的"接收通知的成员"（留空 = 发给应用可见范围内全体）。
- **临时关掉推送（只留网页卡片）**：让技术把服务器 `.env` 里的 `OPS_BRIEFING_PUSH_ENABLED` 设成 `false`。
- **整个简报都停掉**：`OPS_BRIEFING_ENABLED=false`（不建议，等于把耳朵堵上）。
- **改发送时间**：`OPS_BRIEFING_CRON_HOUR` / `OPS_BRIEFING_CRON_MINUTE`（默认 9 / 30 = 早上 09:30）。
  ⚠️ 别调到早上 9 点以前 —— 每天的内容生成(03:00)、分发(07:00)、草稿箱(08:00)、
  公众号数据回流(09:10) 要全跑完，简报才统计得准，否则会把"还没跑到"误报成"零产出"。

## 二、余额 / 欠费告警

### 2.1 我们怎么知道"快没钱了"

三条线，从硬到软：

| 信号 | 判定 | 可靠度 |
|---|---|---|
| ① AI 直接回"额度不足/欠费" | 🔴 红色，立刻充值 | 铁证 |
| ② 阿里云账户余额低于阈值 | 低于 200 元 🟡 / 低于 50 元 🔴 | 准，但**默认没开**，见 2.2 |
| ③ 平时天天花钱、今天突然花 0 | 🔴 红色"疑似欠费/额度耗尽" | 推测，但**永远可用** |

③ 是兜底：它只用我们自己数据库里的花费记录算，**不依赖阿里云任何接口**，
所以就算 ② 一直开不了，也不会出现"没钱了却没人知道"。

### 2.2 关于阿里云余额查询（要技术配合一次）

- 阿里云确实有余额查询接口，代码已经写好了，但**默认关闭**。
- 原因：查余额属于**财务权限**，我们现在用的那把密钥（发短信、存图片、数字人用的）通常没有这个权限。
- 想打开需要技术做两步：
  1. 在阿里云给密钥加上 `AliyunBSSReadOnlyAccess` 权限（子账号还需要**主账号**在"用户中心 → 财务权限"里授权）；
  2. 服务器 `.env` 里设 `OPS_ALIYUN_BALANCE_ENABLED=true`。
- 打不开也没关系：查不到余额时系统会自动退回上面的 ③，简报照发，不会因此漏报。
- **百炼（我们用的 AI）没有"剩余额度查询"接口**，它是直接扣阿里云账户余额的，
  所以看账户余额就等于看 AI 还能用多久；"免费赠送的额度还剩多少"只能去阿里云控制台看。

### 2.3 阈值在哪调

都在服务器 `.env`（改完要重启服务，找技术）：

| 配置项 | 默认值 | 含义 |
|---|---|---|
| `OPS_BALANCE_WARN_YUAN` | 200 | 阿里云余额低于这个数 → 🟡 |
| `OPS_BALANCE_ALERT_YUAN` | 50 | 阿里云余额低于这个数 → 🔴 |
| `OPS_SPEND_DROP_RATIO` | 0.2 | 今天花的钱不到近 7 天日均的 20% → 🟡 |
| `OPS_SPEND_MIN_AVG_CENTS` | 100 | 近 7 天日均低于 1 元的租户不做"骤停"判定（本来就不花钱，别误报） |
| `OPS_MIN_DAILY_CONTENT` | 5 | 今天生成少于 5 篇 → 🟡；等于 0 → 🔴 |
| `OPS_ZERO_STREAK_DAYS` | 3 | 连续 N 天零产出/零分发 → 简报升级为 🚨 强告警标题 |
| `OPS_BUDGET_WARN_PCT` | 80 | 当日预算用掉 80% → 🟡；用满 100% → 🔴 |
| `OPS_HANDOFF_WARN_COUNT` | 5 | AI 客服今日转人工达到 5 次 → 🟡（提醒补 FAQ） |
| `LLM_DAILY_COST_CAP_YUAN` | 50 | LLM 日花费硬上限（元），触顶停止内容生成 → 🔴；0=不限 |
| `LLM_DAILY_CALL_CAP` | 2000 | LLM 日调用次数硬上限，触顶停止内容生成 → 🔴；0=不限 |
| `LLM_DAILY_CAP_ENABLED` | true | 上面两条硬上限的总开关 |

> 每日/每月**预算金额**本身不在这里改，在「今日驾驶舱 → 预算」里自己设。

## 三、外部健康拨测（UptimeRobot）

简报是"我们的系统告诉你它不舒服"；拨测是"**别人**告诉你我们的系统死了"。
服务器整个宕机时，简报也发不出来，只有外部拨测能叫醒你。

### 3.1 配置步骤（一次性，10 分钟）

1. 打开 <https://uptimerobot.com>，注册一个免费账号（免费版够用：50 个监控、5 分钟间隔）。
2. 点 **+ Add New Monitor**，按下表填：

   | 字段 | 填什么 |
   |---|---|
   | Monitor Type | **HTTP(s)** |
   | Friendly Name | `BossMate 生产` |
   | URL | `https://你们的域名/api/v1/health/ping` |
   | Monitoring Interval | **5 minutes** |
   | Monitor Timeout | 30 seconds |

3. 下面 **Select Alert Contacts To Notify** 里勾上要收告警的人。
   默认是注册邮箱；建议在 *My Settings → Alert Contacts* 里再加一个**手机短信**或
   **微信/钉钉 Webhook**，半夜宕机邮件多半没人看。
4. 建议把 **Alert When Down For** 设为 2 次（=连续两次拨测失败才告警），避免网络抖动误报。
5. 保存。正常状态下 UptimeRobot 面板显示绿色 `Up`。

### 3.2 为什么用 `/api/v1/health/ping` 而不是别的地址

- 这个地址**专门给外部拨测用**：会真的去查数据库和 Redis 通不通，
  通了返回 `200`，不通返回 `503`，UptimeRobot 看状态码就够了。
- 它**只返回一个"活/不活"**，不会把队列积压数、磁盘容量、数据库信息暴露到公网 —— 这是安全上的要求。
- ⚠️ 不要拿 `/api/v1/health/full` 当拨测地址：那个是**给技术看的详细体检**，
  会返回内部数据（磁盘、队列、内存），不适合挂在公网被人反复请求。
- 也不要拿首页 `/` 当拨测地址：网页能打开不代表后台在干活（数据库挂了首页照样打开）。

### 3.3 收到 Down 告警怎么办

1. 先自己打开系统网页确认是不是真的进不去（可能只是拨测服务自己抽风）。
2. 真进不去 → 通知技术，告诉他"UptimeRobot 报 /health/ping 503"，
   技术会去看 `/api/v1/health/full` 的详细体检结果。
3. 服务恢复后 UptimeRobot 会自动再发一封 "is back up" 邮件。

## 四、常见问题

**Q：简报里说"3 个公众号未达保底"，我要做什么？**
A：说明当天生成的文章不够分给所有号。去「设置」把每日生成篇数调高，
或者检查是不是某些学科的期刊/选题枯竭了（内容工坊里能看到）。

**Q：简报说"记账失败"是什么意思？严重吗？**
A：严重。意思是**钱已经花出去了，但系统没记上账** —— 后果是花费统计和预算闸都会偏低，
可能超支了还不知道。看到这条直接找技术。

**Q：为什么"今日无内容"的账号不算异常？**
A：因为那太吵了 —— 周末、内容排期、账号轮休都会出现，天天报就没人看了。
真正卡死的情况（登录失效、授权过期、助手离线、连续 3 天没发东西）才会进简报。

**Q：一天里能不能多发几次简报？**
A：不建议。这套设计是"**每天一条，异常置顶**"，不是每出一个小问题就单独推一条 ——
推多了就没人看了。急事有红色置顶，紧急到系统挂了有 UptimeRobot 兜底。

**Q：手动点了「立即体检」，会重复发微信吗？**
A：会，它就是"重新体检并重新推一次"。用来验收配置或补发当天的简报，
不影响第二天早上的自动发送。

## 五、给技术的速查

- 简报代码：`packages/server/src/services/ops/daily-briefing.ts`
- 余额/消耗速率：`packages/server/src/services/ops/supplier-balance.ts`
- 异常事件流水：`packages/server/src/services/ops/incidents.ts`（表 `ops_incidents`）
- 简报快照落库：表 `ops_briefings`（推送成败都落，前端卡片读它）
- 体检数据层：`packages/server/src/services/ops/health-check.ts`（`/health/full` 与简报共用同一份阈值）
- 定时注册：`packages/server/src/services/scheduler.ts` → job type `ops-daily-briefing`
- 手动触发：`POST /api/v1/today/ops-briefing/run`（需登录态），或今日驾驶舱「立即体检」按钮
- 端点：`GET /api/v1/health/ping`（拨测，无鉴权、无内部信息）/ `GET /api/v1/health/full`（详细体检）
